## 2. 已有证据与尚未证实的部分

### 2.1 历史日志中的速度差距

在 70,000～78,000 步区间，对日志中的 tqdm 速度换算为秒/步；按 update 去重，每个实验包含 8,001 个步号：

| 实验 | 平均秒/步 | 中位数秒/步 |
|---|---:|---:|
| 原 HunyuanDualCA + AllRoPE D1 | 0.3640 | 0.3623 |
| D1 + 当前双角色表征监督 | 0.7047 | 0.7042 |

当前每步耗时比历史基线增加约 94%，吞吐量约降至历史基线的 52%。这属于历史运行对比，不是控制机器负载、文件系统状态等因素后的同条件性能实验；tqdm 数值也带平滑与舍入。下一轮需要用同机、同配置、同批次的 wall-clock 测量重新建立基线。

依据：

- [原 D1 正式日志](../AlignDiT_mmdit_base_qknorm_ca_solve_prompt_audio/logs/train_d1_hunyuan_dual_ca_allrope_baseline_config_20260905.log)。不要使用名称不带 `baseline_config` 的中止实验日志；早期中止实验改过 activation checkpointing 等设置。
- [当前双角色实验日志](../AlignDiT_mmdit_d1_hunyuan_dual_ca_allrope_avhubert_dual_role/logs/d1_avhubert_dual_role_20260906_080941_train.log)。

当前实验最初一段约 1.44 秒/步，后期约 0.70 秒/步，与首次提取教师特征、后续复用缓存的实现相符。但不能把后期仍存在的全部差距解释为“每步又运行一次 AV-HuBERT”：**代码只对缓存未命中的样本运行教师**。

### 2.2 已确认的串行缓存处理开销

当前 trainer 在取出 mel/video batch 后，先在训练主进程调用 `audio_teacher.encode(audio_paths)`。缓存命中路径依次执行音频文件身份查询、缓存路径计算、文件存在性检查、逐条 NPZ 读取、元信息和有限值校验、FP16→FP32 转换、CPU padding，最后传到 GPU。该路径没有进入 DataLoader 的 worker 预取流程。

已用现有缓存做过一次额外 CPU 进程的只读小规模计时。每类 batch 的总音频时长约 84 秒，三次读取：

| batch 样本数 | 进程首次读取总耗时 | 三次总耗时中位数 |
|---|---:|---:|
| 4 | 0.121 秒 | 0.059 秒 |
| 8 | 0.098 秒 | 0.059 秒 |
| 16 | 0.144 秒 | 0.076 秒 |
| 32 | 0.245 秒 | 0.114 秒 |

测量范围包含文件身份、读取/验证/类型转换和 CPU padding，不包含 GPU 传输、模型 forward/backward 或 DDP 通信。这里“首次读取”是该进程第一次读该批文件，**没有清理操作系统或共享存储缓存，不能称为严格冷缓存测试**。样本量小，且测量时正式训练仍在运行；结果只说明这条阻塞路径有明显成本，不能直接从总训练时间中扣掉这些数字当作加速预测。

四卡训练会受最慢 rank 的等待影响；不能把单进程读取耗时直接乘以 4。

### 2.3 需要下一轮 profiler 确认的因素

- 表征损失中的 GPU 标量读取、条件判断和动态掩码选择可能触发同步。
- 每步额外的 loss finite-check `all_reduce` 会增加通信和等待。
- 即使全部缓存命中，当前音频教师仍被加载到每个训练 rank 的 GPU；这增加显存占用，但对每步时间的影响尚未独立测量。
- CPU→GPU 传输是否与计算重叠、DataLoader 是否饥饿，以及共享文件系统延迟的实际占比尚未量化。
- 投影头、cosine loss 及其反向传播确实增加计算；其具体成本需要独立测量。

不能提前声称任意单项已经解释全部约 0.34 秒的差距，也不能仅根据一次 GPU 利用率快照判断主要瓶颈。

## 3. 必须保持的实验语义

以下内容在性能优化中保持不变，否则应另建科学实验，而不是称为等价加速：

1. 模型仍为前 6 层 MM-DiT、后 12 层音频 DiT；保留 Hunyuan 双路文本 CA、全头 RoPE、原视觉条件及参考音频处理。
2. 学生监督位置仍为零基索引 5，即第 6 层；100 Hz 音频隐藏状态每 4 帧平均池化到 25 Hz，再经过现有 MLP 投影到 1024 维。
3. 教师仍为 `large_vox_iter5.pt` 的冻结 **audio-only 最终上下文表征**；不能换成 `avhubert_feat` 中的音视频联合特征。
4. 复用本次缓存的 FP16 数值。若只转换容器或分片格式，不重新提取、不做额外归一化、不降低精度；FP16 在 GPU 转回 FP32 应与当前加载得到的目标值一致。
5. 固定时间网格对齐；只在生成掩码与教师真实长度的交集上计算 FP32 cosine。保留空有效区域的可微零损失，不拉伸 padded 长度，不把参考区和 padding 加入监督。
6. 总损失仍为 `flow + 0.1 × mean(CTC_6, CTC_12) + 0.1 × avhubert_rep`。保持现有按 rank 计算有效帧均值、再由 DDP 平均梯度的方式；不能顺手改成跨 rank 的全局帧数加权平均。
7. 教师目标不能成为生成器输入条件；推理不需要目标音频或音频教师。
8. 保留训练样本集合与顺序、动态 batch、seed=666、4 GPU、BF16、每 GPU 9000 mel 帧、最多 32 样本、学习率 5e-5、20k warmup、200 epochs、EMA、音频预训练初始化、checkpoint 保存及样本日志策略。
9. 保留 `checkpoint_activations=False`、`log_samples=True` 和现有 DDP unused-parameter 处理。不要通过减少 batch、关闭样本生成、改变训练精度或减少监督计算频率来制造速度提升。

DataLoader workers、预取数量和存储容器可以作为工程参数单独调整，但必须验证交付给模型的 batch 顺序、有效长度、掩码和目标值没有变化。

若确有缺失，先由独立预处理任务补齐并完成校验，再启动正式训练。保留已有有效缓存；不在训练 worker 中调用 CUDA 教师兜底，不用零特征替代缺失目标。生成完整性报告后将缓存版本视为不可变输入；若原数据或 checkpoint 后续变化，建立新版本并重新校验。

### P1：将教师特征读取移入 DataLoader，启用纯缓存训练

这是第一优先级，也是建议下一轮首先交付的最小优化版本。

目标流程：

```text
启动前：完整性校验 → 固定 feature manifest
DataLoader workers：读取 mel / lip / 教师特征 → collate + 真实长度 → 预取
训练进程：接收 batch → 传到 GPU → 原 D1 + 原表征损失 → backward / optimizer
```

具体要求：

- 将当前 `CustomDataset_mel_video_teacher` 扩展为按 manifest 直接加载音频教师特征，返回 `audio_teacher_features` 与 `audio_teacher_lengths`。样本 ID 必须与其他模态一致。
- collate 保留教师独立长度，不能为迎合 `mel_length/4` 而重复最后一帧或伪造教师帧。
- 首版可继续读取已有 NPZ，先验证 worker 并行与预取收益；不把“必须重新打包全部缓存”作为启动优化的前提。
- 将固定版本的元信息校验移到启动前/索引构建阶段，避免每步重复 `Path.resolve()`、源音频 stat 和 JSON 解析。运行时仍保留读取异常及必要的形状/长度防护。
- 检查 pin-memory 行为，优先以 FP16 暂存目标，降低 host 内存和传输量；在 GPU 上转为 FP32 后进入原损失。核对 Accelerate 实际传输路径，不能只设置 `non_blocking=True` 就声称已经实现重叠。
- 训练模式显式设为拟新增的 `audio_teacher.mode=cache_only`。该字段是规划中的接口，当前代码尚不支持。trainer 在此模式下不得构造 AV-HuBERT 模型；缺失目标在训练开始前报错。
- 保留独立离线提取入口，以便将来建立新缓存；正式训练与提取职责分开。不能让训练进程一边读取一边隐式修改冻结版本。
- 验证训练进程不再导入/加载教师权重，optimizer、EMA 和 generator state_dict 的内容与现有方法一致。

workers 不宜盲目增加：现有 16 workers/GPU 在四卡上已经是 64 个。先保留原设置建立 P1 对照，再尝试每 GPU 4/8/16 workers、`prefetch_factor=2/4`，分别记录 CPU、RSS、共享存储压力和数据等待时间。组合无需全扫，按测量逐步选择；保持有序 batch 交付和随机种子策略。检查 `persistent_workers` 与 `num_workers=0` 的测试兼容性。

### P2：减少确实多余的同步，保留数值与异常保障

只有在 P1 验收后、profiler 显示同步仍占较多时间时推进。

- 静态维度、dtype 和长度范围尽量在 dataset/CPU 阶段确认；避免同样的信息在每步触发 GPU→CPU 标量读取。
- 审查 `_masked_audio_representation_loss()` 的 `valid.sum().item()`、GPU 布尔条件及动态选择。可以比较张量化实现，但必须维持生成区/真实长度掩码、原均值定义和零有效帧时的梯度连接。
- 如果采用完整张量上的 masked cosine，必须在 cosine **之前**处理无效位置；不能依靠 `NaN × 0` 屏蔽无效区域。不能为了省同步而允许 padded NaN 污染有效损失。
- 合并可合并的日志标量传输；继续提供 TensorBoard 的总损失与所有分项，不将“减少可观测性”作为首要优化方式。
- 测量每步 finite-check `all_reduce` 的时间。不要直接删除安全检查；如能与已有同步合并或采用等价检查，必须验证单 rank 异常时所有 rank 能一致退出，不会出现其他 rank 永久等待。
- 不调整教师权重、监督频率、CTC 聚合或 EMA 更新频率。

### P3：存储格式优化，仅在 P1 后仍有 I/O 瓶颈时实施

先用现有 NPZ + worker 预取测量。如果共享存储的小文件打开/元数据请求仍主导，再考虑分片连续存储：

- 推荐候选：按帧连续保存的 FP16 特征分片，加样本 offset/length 索引；或经过实测适合当前存储的只读容器。
- 分片大小先做小规模对比，可从每片 256 MiB～1 GiB 尝试；这是测试起点，不是已经验证的最优设置。
- mmap 不等于没有 I/O；必须测量共享文件系统上的实际随机访问和 page fault 表现。
- 格式转换以已验证的缓存数值为输入，逐样本比较帧数与 FP16 值，全部通过后发布新 manifest。保留旧缓存用于回退，不原地覆盖。
- 若考虑本地 NVMe 暂存，先核实实际可用本地盘、空间和容量；当前 `/zjw524` 是共享挂载路径，不能假定就是本地 NVMe。传输完成、版本校验通过后再读取，并报告一次性暂存成本。
- RAM 缓存仅在测量实际容量后讨论；不能默认将整套特征复制到每个 worker，导致内存按 rank/worker 数倍增。

## 6. 数值正确性验收

先固定相同 batch、模型参数、flow 时间、噪声、生成掩码和 CFG dropout 决策，再比较当前实现与优化实现。仅设置同一个 seed 而不确认上述随机量一致不够。

必须通过：

1. 样本集合与顺序一致；同一 sample ID 的文本、mel、lip、教师特征配对一致。
2. 旧缓存经 FP16→FP32 后与新加载路径目标值逐元素一致；有效长度和 padding 一致。分片转换也逐样本验证，不能只比较均值。
3. 覆盖教师与视频长度略有差异、短样本、不同 padding、无效区域非有限值、零有效监督帧等边界。
4. FP32 参考路径的辅助 loss 建议以 `atol=1e-6, rtol=1e-5` 作为起始检查阈值；BF16 全模型输出/梯度阈值根据旧实现自身重复运行的数值误差确定并记录。超出阈值必须解释，不能不断放宽阈值使测试通过。
5. 投影头和学生应有的梯度保持，教师目标无梯度；推理仍不需要教师。现有 7 项单元测试与 Hunyuan 回归继续通过，并补充纯缓存读取及异常配对测试。
6. 做一个固定 batch 的 optimizer update 对照，比较损失、梯度和更新后参数；多步优化轨迹只要求在已定义的数值容差内，不承诺不同并发/内核条件下全程逐 bit 一致。
7. 四卡检查：无遗漏或重复训练样本、无异常 rank 挂起；变更数据管线后没有偷偷改变 DDP 的损失权重或 batch 分配。

缓存损坏/身份错误必须明确失败。启动前检查结果应一致传达给各 rank，不能只有一个 rank 抛异常、其他 rank 进入训练后等待。

## 7. 性能基准与验收方法

### 7.1 固定条件

本轮结束后，在同一台机器和同样四张 GPU 上顺序执行对照，避免同时运行其他训练或教师预处理。记录 GPU 型号、软件版本、CPU 线程设置、数据位置、workers、预取配置、实际 batch 样本数/长度和缓存状态。

使用相同的固定 batch 序列和相同初始化状态。保持 BF16、9000 帧预算、最大 32 样本与模型超参数一致。包含短/中/长样本 batch，尤其不能只测最快的一类。

建议预热至少 50 步，再测量 500～1,000 步，至少重复 3 次。分别报告：

- 正常训练稳定阶段的 wall-clock 秒/optimizer update、updates/s、p50/p95 batch 耗时。
- DataLoader 等待、目标传输、forward、backward、optimizer/EMA、日志与同步的时间，以及各 rank 的差异。
- GPU allocated/reserved/峰值、CPU/RSS、I/O 和缓存命中/缺失统计。
- 包含 checkpoint 保存和样本生成的完整 epoch 吞吐；短基准没有覆盖这些操作时，不能假装它代表全部运行成本。
- 预处理、格式转换或本地暂存的一次性时间与磁盘容量，单列报告。

端到端计时优先用完整窗口的 wall-clock 边界同步。GPU 分段使用 CUDA events 或短窗口 profiler；CPU I/O 使用独立计时。不要在每个操作后额外 `cuda.synchronize()` 再拿这组受干扰时间当正常训练速度。CPU/GPU 重叠阶段时间不能简单相加解释总耗时。

### 7.2 对照顺序

### 7.3 接受标准

硬性条件：第 6 节正确性检查全部通过；实际训练代码不再调用教师；缺失缓存不被隐式掩盖；CPU 内存、I/O、显存和长尾等待没有不可接受的回归。

速度判据：在重复测量中，优化版端到端平均耗时稳定低于同条件 B，且改善大于运行波动；同时检查 p95，避免平均更快却频繁长时间卡顿。

可将相对当前约 0.705 秒/步降低至少 20%（约 0.56 秒/步）作为**初始工程目标**，但正式判定应以重新测得的 B 为分母。这个数不是预计结果，也不是正确性门槛；若未达到，继续按分段测量定位，而不是修改损失或训练量。历史约 0.364 秒/步只作为参照，不承诺完全恢复。
